##Project Scope & Guidelines

### Project Description

This project aims to create a **hybrid AI coding assistant** with a modular, atomic architecture, able to reason and operate across multiple knowledge domains—such as mathematics, science, English, and programming (TypeScript-centric). Each domain is encapsulated as a discrete module, complete with seeds (data/knowledge), domain-specific tools, and robust orchestration logic. The system is developed in production-grade TypeScript, deployed with best practices for code structure, naming, dependability, and extensibility[2][1].

### General Architecture Principles

- **Hybrid Multi-Domain Engine:** AI model supports modular domains for granular knowledge organization. Domains include English, Grammar, Mathematics, Science, Programming, Typescript, General-Knowledge, Internet/Search, and more depending on scope expansion[1].
- **Atomic Modularity:** Each domain is isolated as a standalone folder/module to guarantee clear separation of logic, seeds, and tools, using explicit file/folder naming conventions (always prefixed by domain)[2][3].
- **Shared Utilities:** Central shared tools facilitate code linting, formatting, calculation, search, and more for cross-domain access. These are housed in `src/ai/shared/tools/` and always prefixed as `shared-*`.
- **TypeScript Production-Readiness:** All files and logic are crafted for real-world usage—no stubs, dummy content, or placeholders. Every exported function and class implements actual business logic with real inputs and outputs, testable in isolation[3].
- **Comprehensive Commenting:** Every file, function, and class must include beginner-friendly, detailed comments explaining purpose, usage, interfaces, and side effects for future contributors[2].

### File Generation Instructions

#### Naming & Syntax Best Practices

- All folders and filenames are **domain-prefixed** and highly descriptive (`mathematics-FibonacciCalc.ts`, `typescript-TSInterfaceGenerator.ts`)[3].
- Use **camelCase** for variables and functions, **PascalCase** for classes and components, and **kebab-case** or **snake_case** for file naming if more readable with multiple modifiers.
- Place all new files in their context folder (e.g., `src/ai/domain/mathematics/tools/`, `src/ai/shared/tools/`).
- Avoid duplicate names—prefix everything with its domain context to maintain uniqueness[2].

#### Metadata & Documentation Standards

- Every file must begin with a metadata block including:
  - **File Purpose:** Succinct description of the functionality.
  - **File Path:** Relative location in the repo.
  - **Dependencies:** List files this module depends on.
  - **Dependents:** List likely modules that import or depend on it.
  - **Creator/Generator:** Credit to assistant or contributor's name.
- Example metadata block:
  ```typescript
  /**
   * File: src/ai/domain/typescript/tools/typescript-TSInterfaceGenerator.ts
   * Purpose: Generates TS interfaces from structured sample data for fast code creation.
   * Depends on: src/ai/shared/tools/shared-DocGenerator.ts
   * Depended on by: src/ai/orchestrator/orchestrator.ts, src/ai/domain/typescript/tools/typescript-TSUnitTestGen.ts
   * Generated by: Vercel v0 Coding Assistant
   */
  ```

- All functions/classes must provide:
  - Purpose and behavior comments.
  - Input and output type documentation.
  - Realistic code logic, not stub/dummy code.
  - Edge cases and error handling notes[3].

- For TypeScript files:
  - Enforce strict typing (`strict` mode in tsconfig).
  - Export only what is necessary, prefer named exports.

#### Logic & Review Standards

- Auto-review generated code for business logic correctness, performance impact, and security patterns—never expose or generate unsafe code.
- Validate code with linter and formatter tools before output.
- If a tool or module interacts across domains, document the interface and expected behaviors in comments.
